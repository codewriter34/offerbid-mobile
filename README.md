# OfferBid Mobile

A hyper-local second-hand marketplace app built with React Native. Replaces chaotic WhatsApp/Facebook trading with a structured, searchable, hub-based catalog and a counter-bidding engine, closing every deal through a WhatsApp handshake for offline payment (cash / MoMo).

**Platform:** React Native (Android-first, iOS-ready)
**Backend:** NestJS (deployed on Render)
**Database:** PostgreSQL (managed)

## Quick Start

```bash
# Clone the repo
git clone https://github.com/Ebesoh-Adrian/offerbid-mobile.git
cd offerbid-mobile

# Install dependencies
npm install

# Copy environment config
cp .env.example .env
# Fill in your API keys in .env

# Start Metro bundler
npm start

# Run on Android
npm run android

# Run on iOS (macOS only)
npm run ios
```

### Prerequisites

- Node.js >= 18
- React Native CLI (`npm install -g react-native-cli`)
- Android Studio + Android SDK (for Android builds)
- Xcode (for iOS builds, macOS only)
- JDK 17

## Architecture Overview

```
[React Native App]
   |-- REST calls (auth, listings, bids) --> [NestJS API]
   |-- WebSocket (Socket.io client)      --> [NestJS Gateway] --> live bid/offer updates
   |-- Cloudinary SDK                    --> Cloudinary CDN (listing photos)
   |-- Firebase SDK (messaging)          --> FCM --> Notifee (display) --> user
   |-- wa.me deep link                   --> WhatsApp app

[NestJS API/Gateway]
   |-- TypeORM/Prisma --> PostgreSQL
   |-- FCM Admin SDK  --> push on bid/offer events
   |-- Resend API     --> OTP + marketing emails
```

The NestJS backend is the **single source of truth** — it owns auth verification, all DB writes, the WebSocket gateway, and triggers both push and email side-effects. The mobile app never talks to Postgres or FCM server keys directly.

## Developer Roles

### Developer A — Core Platform & Listings (Logic/Integration)
- Auth flow (Google OAuth -> JWT)
- Hub selection logic + config
- Create Listing flow (form state, Cloudinary, API submit)
- Feed logic (hub-filtered fetch, filters, pagination)
- Scam Guard enforcement (3-listing limit)
- Profile logic
- **Navigator setup owner**

### Developer B — Bidding Engine, Notifications & WhatsApp (Logic/Integration)
- Bid submission (`POST /bids`)
- Seller Dashboard (Accept/Reject/Counter, timers, 3-bid limit)
- Buyer "My Bids" tracking
- Socket.io real-time subscription handling
- FCM token registration + Notifee display config
- WhatsApp deep-link builder
- In-app notification center logic

### Developer C — UI / Screens (Visual Layer)
- All screen layouts and components
- Design system (buttons, cards, badges, timers)
- Builds screens with mock/static data
- Hands off to Dev A/B for API wiring

**Handoff pattern:** Dev C builds screens with static data and clear prop interfaces. Dev A/B plug in real API calls and state.

## Core User Flows

### Seller Flow
1. Sign in (Google) -> Select hub -> Post item (photos, price, min bid)
2. Receive bid (push notification) -> Accept / Reject / Counter
3. On acceptance -> WhatsApp handshake unlocked -> Meet & close deal offline

### Buyer Flow
1. Sign in (Google) -> Select hub -> Browse/filter feed
2. Submit offer on item -> Wait for response (push notification)
3. If accepted -> Tap WhatsApp button -> Meet & pay offline (cash/MoMo)

### Bidding Loop
1. Buyer calls `POST /bids`
2. NestJS writes to DB, emits Socket.io event to seller's room, sends FCM push
3. Seller acts via `PATCH /bids/:id` -> NestJS updates, emits back to buyer
4. Counter-offers loop until acceptance or expiry

## Development Workflow

### Branch Strategy
- `main` — stable, production-ready code
- `adrian-dev` — Adrian's development branch
- Feature branches: `feature/<feature-name>` off your dev branch

### Commands
```bash
npm start          # Start Metro bundler
npm run android    # Build & run on Android
npm run ios        # Build & run on iOS
npm test           # Run tests
npm run lint       # Lint TypeScript files
npm run type-check # Type check without emitting
npm run clean      # Clean Android build
npm run reset      # Clear Metro cache
```

### Conventions
- TypeScript strict mode enabled
- Path aliases configured (`@components/*`, `@services/*`, etc.)
- One screen per folder with barrel export (`index.ts`)
- Shared components in `src/components/`
- All API contracts from Swagger docs, not guessed

## Data Model Reference

```sql
users        — id, google_id, display_name, phone, hub_id, is_verified, active_listing_count, fcm_token
hubs         — id, country, city, neighborhood, is_active
listings     — id, seller_id, hub_id, category, title, description, starting_price, min_bid, status
listing_images — id, listing_id, cloudinary_url, position
bids         — id, listing_id, buyer_id, amount, status, parent_bid_id, expires_at
notifications — id, user_id, type, payload (jsonb), read
```

Access control is enforced in the NestJS service/guard layer (not DB-level RLS).
